\section{Introduction}

An actuarial answer can be fluent and still fail at the point where the work matters: an assumption may be invented, a reserve formula may be misapplied, a probability may be impossible, or generated code may not reproduce the stated calculation. ActuarialBench measures these observable failures under a controlled protocol. It is a compact empirical study, not a conversational demonstration or a subjective writing contest.

The benchmark's primary contribution is an auditable path from deterministic task generation to preserved model output, objective grading, paired statistical analysis, and a report generated from machine-readable artifacts. The study asks how reliably four black-box language-model routes solve and validate actuarial tasks, where their failure patterns differ, and whether measured differences are large enough to survive uncertainty and multiple-comparison controls.

The analysis deliberately keeps capability, route availability, calibration, latency, and cost separate. A route can score well when it returns a usable answer yet fail more often at the API or schema boundary. Combining those dimensions into one post-hoc score would conceal the operational trade-off and introduce discretionary weights after observing the results.

\section{Research Questions}

The experiment addresses the following questions under the frozen task bank and provider configuration:

\begin{enumerate}
    \item Which route achieves the highest objective actuarial score and exact-correct rate?
    \item Which route produces the most reliable executable actuarial code?
    \item Which route detects planted validation defects and missing assumptions most accurately?
    \item Do any routes introduce unsupported issue codes on missing-information tasks?
    \item How stable are scores across three repeated calls to the same generated task?
    \item How often do schema, timeout, or provider failures prevent capability assessment?
    \item Does reported confidence correspond to exact correctness?
    \item How do results vary across actuarial domains and task formats?
    \item Are pairwise differences statistically supported after multiplicity correction?
    \item What accuracy-latency and accuracy-cost trade-offs are observable from provider-reported metadata?
\end{enumerate}

No question asks which model is universally best. Every conclusion remains conditional on this task portfolio, prompt contract, route configuration, output budget, and experiment date.

\section{Benchmark Design}

\subsection{Experimental unit and task portfolio}

The full bank contains 48 deterministic tasks. Six generated instances cover each of life contingencies, non-life pricing, reserving, risk, statistical modelling, and survival analysis. Validation contributes 12 tasks: six contain planted pricing defects and six withhold assumptions required for a life-insurance calculation. Four routes answered every task three times, creating 576 planned route-task-repetition cells.

The task portfolio is intentionally balanced by generated family, not calibrated to the workload of any particular insurer, qualification syllabus, or national market. Domain means therefore describe performance within this portfolio; they are not prevalence-weighted estimates of production actuarial work.

\subsection{Route configuration}

The configured labels were \texttt{gpt-5.6-sol}, \texttt{deepseek-v4-flash}, \texttt{claude-opus-5}, and \texttt{glm-5.3}. All were accessed through AgentRouter. Route identities are provider assertions and were not independently verified. The OpenAI Responses transport was used for GPT and DeepSeek, the Anthropic Messages transport for Claude, and OpenAI Chat Completions for GLM. Claude preserved separate system and user messages; compatible routes received the same content through their supported prompt transport.

Each request used a fresh context and a 2,000-token output budget. DeepSeek and GLM used the configured low reasoning effort. Requests ran concurrently across routes but sequentially within each route, so no route key had more than one call in flight. The manifest records route metadata, prompt and task hashes, random seeds, retry policy, timestamps, and the Git commit used for execution.

\section{Actuarial Task Construction}

\subsection{Generated numerical and component tasks}

Fixed-seed generators produced novel parameter combinations while retaining analytic ground truth. Life tasks multiply age-specific annual survival factors. Pricing tasks compute frequency, severity, pure premium, and aggregate variance under a compound model. Risk tasks evaluate lognormal value-at-risk and tail value-at-risk components. Statistical tasks recover exponential maximum-likelihood quantities, while survival tasks reconstruct Kaplan-Meier components.

Multi-component scoring gives credit only for the components that meet their predefined tolerances. This avoids treating an answer with one correct intermediate value as either wholly correct or wholly wrong. Exact correctness still requires full credit on every required component.

\subsection{Coding tasks}

Reserving tasks require a Python function for Chain Ladder calculations. Generated code is parsed with an abstract-syntax-tree allowlist, limited to one required function, and executed in an isolated Python subprocess with restricted built-ins and a short timeout. Hidden cases check both execution and actuarial output. This mechanism reduces accidental host access but is not a hardened security sandbox.

\subsection{Validation and missing-information tasks}

The planted-defect tasks encode exact issue identifiers for negative exposure, overdispersion, future-data leakage, and impossible probabilities. Missing-information tasks require the route to identify absent mortality and interest assumptions without adding unsupported issue codes. Precision, recall, F1, and critical-defect recall follow directly from the expected and reported issue-code sets.

This design makes validation grading reproducible, but it also narrows what can be claimed. The benchmark measures recognition of the injected defect taxonomy. It does not grade the full quality of an actuarial model-validation memorandum or prove that a route would detect novel defects outside the frozen set.

\section{Ground Truth and Grading}

Reference answers are computed independently of model output using deterministic Python and actuarial formulas. Each task stores its seed, expected values, component tolerances, metadata, required concepts, and grading policy. Unit tests exercise generator invariants such as bounded probabilities, finite reserves, non-negative risk measures, and reproducible task hashes.

Numerical values use task-specific absolute and relative tolerances through \texttt{numpy.isclose}. Coding answers receive separate execution and hidden-case component scores. Diagnosis answers use exact set comparisons. The parser accepts a JSON object and tolerates surrounding code fences or recoverable surrounding text, but it records schema violations rather than silently inventing missing fields.

The primary score is the arithmetic mean of objective component scores. \emph{Exact correct} means a score of one. Explanation checks are recorded as secondary evidence and do not replace mathematical or code correctness. Provider and timeout failures remain tagged separately from model-content errors.

\section{Experimental Controls}

Every route received the same task text, system instructions, task order, maximum output budget, grading rules, and reference answers. Each task began with a fresh context. Repetition identifiers were preserved rather than averaging or selecting the best response. Raw text, parsed output, component scores, latency, token counts, finish reason, route metadata, and error state were written for every call.

The lowest-common-denominator policy cannot make heterogeneous APIs identical. Prompt transport differs for Claude, and provider-side routing or hidden model updates may differ across labels. Those deviations are recorded instead of being treated as controlled model properties. Provider-reported cost was accepted only when supplied; no public price list was retrofitted to calls after execution.

The experiment directory is append-only in normal operation. Its core artifacts are \path{manifest.json}, \path{responses.jsonl}, \path{scores.jsonl}, and \path{analysis.json}. The published run contains all 576 planned cells without duplicates or omissions.

\section{Statistical Methodology}

\subsection{Capability and operational views}

Two views prevent route failures from being mistaken for mathematical errors. The all-call mean retains every planned call and assigns the recorded zero score to API or timeout failures. The capability mean excludes those failures and estimates performance conditional on receiving a gradeable route response. Both are reported with their denominators.

Schema failures remain in the capability view because the route returned content but did not satisfy the common output contract. Schema-failure rates use capability observations as their denominator. Calibration metrics use capability rows with a reported confidence value, so they should not be read as unconditional calibration of unavailable or unparsable responses.

\subsection{Uncertainty and paired comparisons}

Bootstrap 95\% intervals use 2,000 fixed-seed resamples of observed scores. Pairwise comparisons align routes on task and repetition and exclude a cell when either route has an API or timeout failure. The paired sign-permutation test evaluates the mean score difference, while paired Cohen's $d_z$ describes standardized effect size. Exact McNemar tests compare discordant exact-correct outcomes on the same aligned cells.

Six pairwise route comparisons create a multiple-testing problem. Holm adjustment is applied separately to permutation and McNemar $p$-values. A descriptive lead is called statistically supported only when the point estimate favors the route, the interval excludes zero, and the adjusted test supports a difference. This rule prevents small ranking changes from becoming unsupported winner claims.

\subsection{Reliability and calibration}

Repeat agreement is the share of tasks whose available repetition scores are identical. Mean within-task standard deviation measures the magnitude of repeat variation without confounding it with different task difficulty. The Brier score compares confidence, scaled to $[0,1]$, with exact correctness. Five equal-width confidence bins support the reliability plot; sparse bins are shown only when they contain observations.

\section{Limitations and Threats to Validity}

\textbf{Construct validity.} The bank measures objective numerical, component, coding, and issue-code outcomes. It does not cover regulatory writing, expert judgement under ambiguous policy wording, long-horizon workflow execution, or human review quality. The validation subset reached a ceiling and should be expanded before comparative claims are made in that domain.

\textbf{External validity.} Forty-eight generated tasks form a useful portfolio study but not a representative sample of all actuarial work. Six tasks within most domains are parameter variants of one family, so domain breadth is narrower than the task count alone suggests. Results should not be generalized to a different jurisdiction, provider, prompt, tool environment, or model version.

\textbf{Route identity and serving conditions.} AgentRouter controls routing and asserts the model labels. The study cannot verify underlying weights, quantization, system prompts, batching, or provider updates. Latency and no-text failures may reflect serving conditions rather than intrinsic model capability.

\textbf{Protocol comparability.} The content contract was shared, but API transports differed. Claude received distinct system and user fields while compatible routes received the supported combined transport. DeepSeek and GLM used low reasoning effort. The common 2,000-token limit may disadvantage routes that spend more output budget before emitting the requested JSON.

\textbf{Statistical precision.} Three repetitions expose stochastic variation but remain a small sample of future responses. Bootstrap and permutation results describe the observed task-repetition portfolio; they do not remove dependence among generated variants or guarantee stability after provider changes. Pairwise capability tests omit cells with route failures, while all-call metrics retain them.

\textbf{Grading and execution.} Ground truth and graders are tested, but any reference implementation defect would propagate systematically. Restricted subprocess execution is not container isolation. Confidence calibration is conditional on reported confidence, and the unsupported-issue proxy checks issue codes rather than every unsupported statement in free-form explanations.

\section{Conclusion}

ActuarialBench answers its central question with a qualified result. Claude and GPT formed the leading group under this protocol: Claude achieved the highest capability partial-credit mean, while GPT produced the most exact-correct calls and no route failures. Their mean capability difference was not statistically supported after correction. Both showed clearer paired advantages over DeepSeek and GLM, although performance varied materially by domain, task format, and operational outcome.

The experiment also identifies where the benchmark itself must improve. Validation tasks were too easy to distinguish the routes, provider cost was unavailable, and generated variants provide depth within families rather than broad coverage of actuarial practice. The defensible contribution is therefore not a universal leaderboard. It is a reproducible record of what each route solved, where it failed, how stable the result was, and which observed differences survived paired uncertainty analysis.

\section{Reproducibility Checklist}

\begin{enumerate}
    \item Create a Python 3.11 or later environment and install \texttt{pip install -e ".[dev]"}.
    \item Run \texttt{pytest} to verify task generators, graders, provider transports, retries, analysis, and report assets.
    \item Set route keys through the environment variables documented in \texttt{.env.example}; never place keys in source files.
    \item Run \texttt{python run\_benchmark.py --smoke} for the bounded eight-task route check.
    \item Run \texttt{python run\_benchmark.py --repetitions 3 --parallel-models} only when the full API cost and scope are authorized.
    \item Analyze an immutable experiment with \texttt{python analyze\_results.py results/raw/EXPERIMENT}.
    \item Generate report assets with \texttt{python generate\_report\_assets.py results/raw/EXPERIMENT}.
    \item Compile this report twice with \texttt{pdflatex -interaction=nonstopmode -halt-on-error main.tex}.
\end{enumerate}

The raw experiment contains 576 response records and 576 score records. The manifest freezes 48 task hashes, the shared prompt hash, route configuration, seed, repetitions, and execution commit. Generated tables and figures read from \texttt{analysis.json}; benchmark scores are not typed manually into this document.
